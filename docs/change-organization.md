# Organizing changes

These rules adapt the Rocket.Chat repository's
[change organization guidelines](https://github.com/RocketChat/Rocket.Chat/blob/develop/docs/change-organization.md)
to the desktop app. For the branches themselves (`dev`, `master`,
`release/X.Y.x`), read [development-and-release-flow.md](development-and-release-flow.md).

Each change must be easy to review alone and easy to revert alone. With more
code generated by tools, this matters more, not less. A reviewer can follow one
concern at a time, and a revert must never take unrelated work with it.

## One concern per pull request

Classify each change before you write it:

- **fix**: changes a wrong behavior. It ships with a test that fails without it. For a
  visual fix that no test can see, a screenshot before and after the fix
  replaces that test.
- **refactor**: changes structure, not behavior. The existing tests stay green
  without edits.
- **feature**: adds behavior.
- **test / chore / ci / docs**: everything else.

A pull request carries one classification and one concern. Each of these goes
in its own pull request:

- an edit made "while I am here"
- a flag or a condition for a case that does not exist yet
- a change that a reviewer would call "not related"

When you find a problem outside the concern, do not fix it in the same pull
request. Report it in the PR description or open an issue for it.

## Title the pull request after what changes

`dev` accepts squash merges only. The squash commit takes the PR title, or the
commit subject when the pull request has one commit. That line is what people
read in the release notes and in `git log`, without the code in front of them.

The title says **what** changes, not **how** the code does it. The diff already
shows the mechanism.

- **fix**: name the behavior that changes for the user:
  `fix: reload the workspace after a storage wipe even when the page blocks unload`,
  not `fix: handle beforeunload in the reload path`.
- **feature**: name what someone can now do.
- **refactor**: name the area and the goal, such as
  `refactor: move the settings into their own window`. Here the "how" is the
  change.

If the title needs "so", "by" or "to avoid" to explain itself, the part after
that word is usually the real title.

Put the Jira key at the end, in parentheses:
`fix: keep injected.ts running before the page defines process (DSK-242)`. The
key is the only internal reference that a public title or commit body may
carry.

## Order work as a stack

When a feature needs fixes or enabling refactors, order them: **fixes →
refactors → feature**. A change that does not depend on the feature goes
straight to `dev` instead of into the stack.

This also applies to exploratory work. A proof of concept can live in a single
pull request, but its history already has the shape of a stack:

- Commit each fix or refactor as its own commit when you finish it. Never fold
  it into a feature commit.
- Keep fixes and refactors below the feature commits. Reorder them with
  `git rebase`. Use `git commit --fixup` with `git rebase --autosquash` to keep
  each follow-up attached to its commit.
- Make each commit build and pass the tests on its own, so that you can extract
  it without changes.

Then extract them one at a time into their own pull requests off `dev`, until
the original pull request holds only the feature. If the proof of concept is
dropped, still extract its fixes and enabling refactors. That work is not lost
with the feature.

When a large mixed pull request already exists, propose the split before you
touch it. Show a table with each concern, its files, its size and its
dependencies.

## Work with a stack

`dev` squash-merges each pull request, so a child's history no longer contains
its parent's commits after the parent lands:

- When a parent merges, rebase the child onto `dev` from the parent's **old**
  tip: `git rebase --onto origin/dev <old-parent-tip> <child>`. Do not merge
  `dev` into a branch that still carries the parent's original commits. That
  merge can cause conflicts, such as renames and moved files, that are not
  related to the child.
- When a parent is rewritten, retarget its children (or rebase them), so that
  their diffs show only their own changes.
- After a rebase that resolved conflicts automatically, check the tree. The
  pull request's own files must be unchanged, and every other file must match
  the new base. A replayed older commit can silently revert newer base content,
  such as a dependency bump or another person's change.
- If `dev` changed one of the pull request's files for an unrelated reason,
  merge that file three ways (`git merge-file`). Do not copy either side.
- A fix for a shipped stable version lands on `dev` first. Then cherry-pick it
  onto the `release/X.Y.x` branch in its own pull request.
